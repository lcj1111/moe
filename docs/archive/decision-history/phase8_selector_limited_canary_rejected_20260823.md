## 结论

2026-08-23 在 gpu-111 执行的有效有限 canary 判定为 **rejected**。384 个请求全部完成且零失败，placement-plan 在显式激活前未应用、激活后 8 个 rank 的哈希完全一致，原 SGLang 服务也已成功恢复；唯一失败项是恢复段 p99 未回到稳定段的 105% 以内。

因此，本轮不得继续执行 trigger、cooldown、rollback 自动闭环验收，也不得降低既定的 105% 门槛。

## 可靠性边界

本报告足以判定“这一次冻结有限 canary 未通过”，但不足以单独证明恢复尾延迟在长期运行中必然超标。每阶段只有 128 个请求，p99 主要由最慢约 1–2 条请求决定；本轮也只覆盖一次服务启动、一次迁移和一次恢复，仍可能受编译缓存、GPU 热状态与瞬时调度影响。

若要判断该问题是否稳定复现，应另行预注册至少 5 轮配对复测。每轮三阶段内部必须复用相同请求流，轮间更换 seed，且从干净服务状态开始；最终同时报告各轮恢复比值、跨轮 p95 和 bootstrap 置信区间。在新复测完成前，本轮 `rejected` 上线结论保持有效，不能据“样本可能波动”提前放行自动闭环。

## 运行中发现并修复的问题

1. 首次启动时，虚拟环境 Python 的符号链接被展开到 `/usr/bin`，导致 worker 找不到 `ninja`。修复为保留配置中的虚拟环境 `bin` 路径，并增加启动前校验。
2. 初始编排按固定 EPLB 调用次数激活 plan；实际 384-token 解码触发的周期多于估计，污染了稳定段。修复为稳定段完成后写入带 map 哈希的显式激活文件，并在 Gate 中审计日志字节边界。
3. 初始三段使用不同 seed，造成输出长度分布不可比。修复为三段复用完全相同的请求流，并在分析器中逐条校验六个身份字段。
4. vLLM 退出后僵尸主进程曾阻塞服务恢复。修复为忽略纯僵尸进程组并主动回收子进程。

以上异常尝试均保留在服务器独立目录中，仅作为故障审计证据，不作为 canary 结论。最终结论只来自机器清单所指向的有效输出目录。
